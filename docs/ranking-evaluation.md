# AI-Assisted Ticket Ranking — Quality Evaluation

## Overview

Context AI uses a weighted scoring algorithm to recommend which customer-support tickets staff should handle first.

This evaluation investigates whether the algorithm places important tickets near the top of the queue, how it compares with simpler ranking strategies, and how each scoring component affects ranking quality.

The evaluation measures:

- Normalised Discounted Cumulative Gain at rank 10 (NDCG@10).
- Critical-ticket Recall@10.
- Performance against customer-priority and oldest-first baselines.
- Feature ablation, removing one scoring component at a time.

This is a controlled evaluation using illustrative synthetic tickets, not a validation study on real customer-support records.

## Evaluation Dataset

The dataset contains **24 manually constructed ticket scenarios**, with six labelled as critical.

Each ticket contains a scenario description, customer-selected priority, simulated AI urgency, simulated AI escalation risk, timestamps and a manually assigned relevance label.

### Relevance Labels

| Label | Meaning | Description |
|---|---|---|
| 3 | Critical | Issue requiring immediate attention |
| 2 | High | Important issue requiring prompt attention |
| 1 | Normal | Routine support request |
| 0 | Low | Minor or informational request |

Labels were assigned from the scenario descriptions rather than calculated using the ranking algorithm.

This avoids directly defining the expected ranking using the same formula being evaluated.

However, the labels are subjective and have not been independently reviewed or validated by customer-support professionals.

The AI urgency and escalation-risk values are also simulated rather than generated by Groq for these scenarios.

Some scenarios deliberately contain misleading priority signals to test failure behaviour.

## Evaluation Metrics

### NDCG@10

NDCG measures how closely a ranking matches an ideal ordering of the labelled tickets, with greater rewards for placing highly relevant tickets near the top.

Discounted Cumulative Gain is calculated as:

\[
DCG@k = \sum_{i=1}^{k} \frac{2^{rel_i}-1}{\log_2(i+1)}
\]

NDCG divides this value by the DCG of the ideal ranking:

\[
NDCG@k = \frac{DCG@k}{IDCG@k}
\]

A score of 1 represents an ideal ordering within the evaluated cutoff. Higher values indicate better agreement with the assigned relevance labels.

### Critical Recall@10

Critical Recall@10 measures the proportion of all critical tickets that appear within the first ten recommendations.

\[
Recall@10 = \frac{\text{Critical tickets in top 10}}{\text{Total critical tickets}}
\]

In this evaluation, tickets with relevance label 3 are considered critical.

With six critical tickets in the dataset, retrieving five within the top ten produces:

\[
Recall@10 = \frac{5}{6} = 83.3\%
\]

Recall measures coverage rather than the precise ordering of critical tickets within the top ten.

## Compared Ranking Methods

### Weighted AI-Assisted Ranking

The production algorithm uses:

\[
S = 0.45U + 0.25E + 0.15C + 0.15W
\]

Where:

- U = AI urgency.
- E = AI escalation risk.
- C = customer-selected priority.
- W = waiting-time score.

### Customer-Priority Baseline

Tickets are ordered by customer-selected priority, with HIGH before MEDIUM before LOW.

Ties are resolved using ticket age and then ticket ID.

### Oldest-First Baseline

Tickets are ordered by creation timestamp, oldest first.

Ticket ID is used to resolve timestamp ties.

### Feature Ablation

Each ablation experiment removes one scoring component by setting its weight to zero.

The remaining weights are renormalised to sum to 1.

The four ablations remove:

- AI urgency.
- AI escalation risk.
- Customer priority.
- Waiting time.

These experiments use the same synthetic dataset as the full model.

## Results

### Baseline Comparison

| Ranking method | NDCG@10 | Critical Recall@10 |
|---|---:|---:|
| Weighted AI-assisted ranking | **0.8210** | **83.3%** |
| Customer-priority baseline | 0.5915 | 50.0% |
| Oldest-first baseline | 0.2830 | 16.7% |

The weighted ranking achieved higher NDCG@10 and critical recall than both baselines on this dataset.

It retrieved five of six critical tickets in the top ten, compared with three for customer-priority sorting and one for oldest-first sorting.

The NDCG@10 difference between the weighted ranking and customer-priority baseline was 0.2295.

This is an improvement on the specific illustrative dataset, not an estimate of real-world performance.

### Feature-Ablation Results

| Experiment | NDCG@10 | Critical Recall@10 |
|---|---:|---:|
| Full weighted algorithm | 0.8210 | 83.3% |
| Remove AI urgency | 0.8162 | 83.3% |
| Remove escalation risk | 0.7207 | 66.7% |
| Remove customer priority | **0.8617** | 83.3% |
| Remove waiting time | 0.8249 | 83.3% |

Removing escalation risk reduced NDCG@10 from 0.8210 to 0.7207 and critical recall from 83.3% to 66.7%.

Removing customer priority increased NDCG@10 to 0.8617 while leaving critical recall unchanged.

Removing waiting time also produced a small NDCG@10 increase.

These results demonstrate that feature contributions depend on the dataset and that the current manually selected weights are not necessarily optimal.

The results do not justify changing production weights without a larger, independently labelled evaluation.

## Failure-Case Analysis

### False High Priority — Ticket T19

**Scenario:** Minor spelling mistake on a help page.

**Human-assigned relevance:** 0 (Low).

**Simulated inputs:**

- Customer priority: HIGH.
- AI urgency: HIGH.
- AI escalation risk: HIGH.

**Observed outcome:** Ranked second, with a priority score of 85.31.

The ranking algorithm gave this minor issue a high position because all three supplied priority signals indicated high importance.

This demonstrates how incorrect upstream classification signals can cause a deterministic weighted ranking algorithm to prioritise an unimportant ticket.

### Missed Critical Ticket — Ticket T02

**Scenario:** Possible account takeover and unauthorised access.

**Human-assigned relevance:** 3 (Critical).

**Simulated inputs:**

- Customer priority: LOW.
- AI urgency: LOW.
- AI escalation risk: LOW.

**Observed outcome:** Did not appear in the top ten.

This demonstrates that a genuinely critical issue can be missed when all supplied severity signals underestimate its importance.

These examples were deliberately constructed. They are not observed Groq classification failures or incidents from real customer-support traffic.

## Interpretation

The weighted algorithm outperformed both simple baselines in this experiment, suggesting that combining multiple signals can produce a more useful ordering than relying only on customer priority or ticket age.

However, the failure cases show that deterministic scoring does not eliminate errors in the underlying signals.

The ablation experiments also reveal that the manually chosen weights are not consistently beneficial on this dataset.

The evaluation therefore supports further investigation rather than a claim of production-level ranking accuracy.

## Testing and Reproducibility

The ranking metrics are implemented in:

`lib/tickets/ranking-metrics.ts`

Their unit tests cover:

- Perfect and imperfect NDCG rankings.
- A manually calculated NDCG example.
- Zero-relevance edge cases.
- Non-mutation of the original dataset.
- Full, partial and zero critical-ticket recall.
- Empty-critical-set behaviour.
- Top-k cutoff behaviour.

The ranking algorithm itself is separately covered by unit tests.

At the time of this evaluation, all **20 ranking-related unit tests passed**.

### Run Unit Tests

```bash
npx vitest run lib/tickets/priority-scoring.test.ts lib/tickets/ranking-metrics.test.ts
```

### Run the Evaluation

```bash
npx tsx benchmarks/priority-ranking.evaluate.ts
```

The script prints the baseline comparison, feature-ablation results and the full model's top ten recommendations.

## Limitations

1. **Small dataset:** Only 24 illustrative cases were evaluated.
2. **Subjective labels:** Relevance was manually assigned without independent expert review.
3. **Simulated AI signals:** The evaluation does not measure Groq's actual classification accuracy.
4. **Constructed failure cases:** Some incorrect severity signals were deliberately introduced.
5. **Single dataset:** Results have not been replicated across independent samples or business contexts.
6. **No statistical uncertainty:** Confidence intervals and significance testing were not calculated.
7. **Limited metrics:** NDCG@10 and Critical Recall@10 do not capture all operational outcomes, such as resolution time, customer satisfaction or SLA compliance.

Because of these limitations, the reported metrics should not be described as verified production accuracy or generalisable improvements.
